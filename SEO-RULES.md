# Permanent SEO & Pre-Launch Rules — HTML / CSS / PHP Website

> Standing SEO rules for this repo (linked from AGENTS.md). Read and follow `SEO_LAUNCH_CHECKLIST.md` before shipping any website change. These instructions apply to the entire website, not only the homepage.

## Project context
- Production domain: `https://sushantrana.com` (apex, no www; `.htaccess` sends www and http there in one 301).
- Business: Sushant Rana, business growth consultant (performance marketing, SEO, websites, CRM, AI automation), Chandigarh, India; clients in India, the UAE, the USA, Canada and Australia. Language: English.
- Stack: static HTML pages (`<folder>/index.html`, never PHP pages) on Hostinger; PHP only for `api/`. Shared header/footer stamped by `dev/sync-layout.py`; service/industry/case pages generated by `dev/page-gen/`.
- Canonical URLs always end in `/` and match the folder: `https://sushantrana.com/services/google-ads/`.
- Automated check: `python3 -I dev/seo-audit.py` (must end with 0 FAIL before a push).
- SEO source of truth: `SEO_LAUNCH_CHECKLIST.md` + `GEO_AEO_AIO_CHECKLIST.md` (GEO, AEO, AI search readiness) plus Google's current Search Central documentation. Latest audit: `AI-SEARCH-AUDIT.md`.

## Mission
- Treat search crawlability, indexability, semantic HTML, human-first content, accessibility, speed, safe deployment and measurement as requirements of every change.
- Never claim "SEO done," "Google indexed," "rank #1," "schema rich result guaranteed," or "passed" without direct evidence.
- Preserve working designs, features, URLs, analytics, lead forms, security, and performance. Explain risky changes before making them.
- Do not keyword-stuff, generate doorway/location-spam pages, create fake reviews, buy ranking links, or automatically submit to low-quality directories.

## Mandatory workflow on EVERY coding task
1. Discover the actual project structure, routing, PHP templates/includes, existing SEO settings, `.htaccess` or server config, and page inventory. Do not assume paths or files exist.
2. Identify whether the change affects metadata, content, internal links, status codes, canonical URLs, structured data, rendering, accessibility, robots/sitemaps, performance, forms, or analytics.
3. Read relevant checks in `SEO_LAUNCH_CHECKLIST.md`; scan shared templates so fixes apply across all applicable pages.
4. Implement the smallest maintainable change; do not add duplicate metadata from both an include and a page. Prefer shared PHP helpers/templates with per-page values.
5. Validate PHP syntax (`php -l` on changed PHP files), inspect rendered HTML and actual HTTP headers/status where an environment exists, test responsive layouts and forms. Run existing project tests; never invent test results.
6. Report: changed files, affected routes, tests actually run (pass/fail), unresolved findings (P0/P1/P2), launch blockers and anything requiring manual production verification.
7. If asked for an SEO audit or launch approval, cover ALL relevant sections of the checklist, not just files touched.

## Page-level SEO requirements
- Each intentional, indexable URL has a distinct, accurate, concise `<title>`, useful unique `<meta name="description">`, one clear primary H1, sensible H2/H3 hierarchy, real helpful content and descriptive internal links.
- There is no mandatory title character count, description length, keyword density, or word count. Optimize usefulness and presentation rather than arbitrary targets.
- Do NOT add a `meta keywords` tag for Google SEO. Avoid duplicate/missing/conflicting tags.
- Use semantic HTML (`html[lang]`, `main`, `header`, `nav`, `footer`, forms and labels), descriptive image `alt` where informative, empty alt for decorative images, and descriptive link/CTA text.
- Serve primary copy and crawlable `<a href="...">` internal links in server-rendered HTML whenever practical; do not hide essential text exclusively in CSS-generated content or interactions.
- Use logically structured readable URLs. Preserve URLs with existing inbound links and implement mapped 301/308 redirects when needed; verify destination and avoid redirect chains.
- Internal links should lead to a valid destination (no broken links, unnecessary nofollow, or orphaned pages). Breadcrumbs only when they reflect the site's hierarchy.
- Localized/translated pages: add correct reciprocal hreflang only when genuine alternate-language/region URLs exist; otherwise do not add hreflang.

## Technical crawlability / indexing
- Choose one production origin: HTTPS and preferred hostname. Use permanent redirects for alternate hostname/protocol and trailing-slash variants only as appropriate; no redirect loops.
- Each canonical, indexable URL should return HTTP 200 and include an absolute, appropriate self-referencing `rel="canonical"` unless another canonical is intentionally warranted. Exclude query tracking parameters from canonical URLs.
- Never build canonical or structured-data URLs from untrusted `HTTP_HOST` without validated production configuration. HTML-escape rendered metadata; safely JSON-encode JSON-LD.
- Exclude intentional non-public, duplicate, transactional, search-result or success pages from indexing with correctly applied `noindex` where appropriate; do not hide a `noindex` page behind robots.txt if relying on Google to see it.
- Staging MUST be protected using authentication or equivalent access restriction; do not rely on robots.txt alone for private staging.
- On production launch, remove unintended global `noindex`, `X-Robots-Tag: noindex`, and `Disallow: /` on the PUBLIC site. Check both page markup and response headers. Do not expose sensitive routes.
- Create/validate `/robots.txt` and `/sitemap.xml` (or sitemap index) at the live origin. Sitemap contains only absolute canonical, indexable, HTTP-200 URLs. Use correct `lastmod` only if actual content changed.
- Return genuine HTTP 404 for missing resources, 410 for permanently removed resources when justified, and appropriate 301/308 for actual moves. Avoid soft 404s and redirecting every missing URL to home.
- Check that CSS, JS, images and important page content needed for rendering are accessible to crawlers, and that links are not blocked by login, WAF, or misconfigured rules.
- Apply `noindex` and robots restrictions intentionally and individually, not as a blanket rule to all PHP files or all query parameters.

## Structured data / social
- Prefer valid JSON-LD matching content visible on the page and supported use cases; use Organization (or relevant subtype), WebSite, BreadcrumbList, LocalBusiness, Product, Article, etc. ONLY when genuinely applicable.
- Include accurate required/recommended fields for the specific Google rich-result feature. Never fabricate ratings, prices, identities, business hours, addresses, authors, availability, or testimonials.
- Validate with Google Rich Results Test for Google-supported features and Schema Markup Validator for general schema.org syntax. Markup does NOT guarantee rich results.
- Add accurate Open Graph/Twitter preview metadata and share images if useful; those are social previews, not ranking guarantees.

## Performance, UX, accessibility and PHP quality
- Aim for good field Core Web Vitals at the 75th percentile: LCP <= 2.5 s, INP <= 200 ms, CLS <= 0.1; assess real-user field data when available, not only a lab score.
- Optimize appropriately sized/compressed images (WebP/AVIF where supported), responsive `srcset`, font loading, cache headers, CSS/JS payloads, and server/hosting performance. Never lazy-load the LCP hero image without evidence that doing so helps.
- Use viewport meta, responsive layouts, visible focus states, accessible navigation, sufficient text contrast, logical headings, form labels and helpful validation/errors. Do not sacrifice UX for a test score.
- In PHP, use reusable safe meta/rendering helpers, output escaping, input validation, CSRF protection on state-changing forms, safe sessions, parameterized database queries (if applicable), and PHP/server error logging. Disable public debug traces and directory listings.
- Set correct status code/header behavior before PHP body output. Verify cache policy does not accidentally serve private data or stale SEO metadata.

## Analytics, lead tracking and launch
- Configure/verify Google Search Console domain or URL-prefix property, sitemap submission and URL inspection AFTER the production domain is accessible; never claim verification/submission without access.
- Configure/verify GA4 and GTM only when required by project; obtain appropriate user approval and implement consent handling as applicable. Avoid duplicate page_view and conversion firing.
- Test contact forms end-to-end: validation, submission, email/database integration, success message or thank-you page, spam safeguards, duplicate prevention and any conversion event.
- Add local business profile/citations only for a real eligible business; use consistent public NAP details (name/address/phone) only where accurate.
- Before deployment: produce a page-by-page SEO report and flag **P0 launch blockers** (global noindex, broken essential pages, wrong canonical origin, unsafe production exposure, core forms failing, severe routing/crawl errors).
- Deployment changes must have a rollback path or backup; run post-deploy crawl, status/header verification, mobile tests and Search Console manual tasks.

## Backlinks and off-page: recommendation only unless authorized
- Research useful industry publications, partnerships, expert citations, relevant authentic listings, unlinked brand mentions, and original assets worthy of editorial links.
- Do not send outreach, modify third-party profiles, buy ads/links, submit directories, or create accounts without the owner's explicit authorization.
- Paid/sponsored placements must use appropriately qualified `rel="sponsored"` or `nofollow` links. User-generated outbound links usually need `rel="ugc"`/`nofollow` as applicable.
- Prioritize relevance, legitimacy and referral value; don't report backlink volume or third-party authority scores as guaranteed ranking signals.

## Required audit deliverable
For each issue, include: **Priority (P0/P1/P2) | URL/route | issue | exact file/line if available | evidence | safe fix | test/verification | status (PASS/FAIL/NOT TESTED/N/A)**.
Finish with: **GO / NO-GO / CONDITIONAL GO**, open blockers, manual owner actions, and a post-launch plan (day 0, first week, first 30 days).
